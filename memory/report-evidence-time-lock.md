# 报告／数据源独立性与时间锁（2026-06-30 用户拍板）

## 目的

保证早报、午报、晚报分别形成可复算、可比较、参数足够准确的独立样本。样本准确性优先于用后续时段数据“补鲜”前序报告。

## 宪法规则

1. 每份报告绑定唯一证据快照：`交易日 + slot + 实际采集时间 + 来源哈希`。
2. 报告独立：早／午／晚各自从绑定快照完成验真、转录、分析、评分、胜率、风险与决策；不得复用前序或后序判断。
3. 数据源独立：后续时段采集不得覆盖、替换、补鲜、重新解释或替前序报告通过 freshness 门。晚报源与午报源必须逻辑和存储隔离。
4. 时间锁：分析锁建立后，该报告的样本时间与来源哈希冻结。发布延迟不改变样本时点；正文 quote 必须写真实采集时段。
5. 若用户明确要求交付已锁定时点的报告，继续使用该报告自己的证据快照，不吸收后来采集。该报告是时间截面样本，不能伪装成后续时点的实时计划。
6. freshness 校验必须针对“报告绑定的证据快照”，不能只检查共享 inbox 中后来被覆盖文件的最新 mtime。
7. Notion、Word、台账和 deliver 必须引用同一报告哈希、同一 slot、同一证据快照；禁止混用晚报截图给午报完成收尾。

## 工程要求

- 采集产物应按 slot 或 capture id 版本化保存，不能只保留会被后续采集覆盖的共享文件。
- transition／analysis lock 应记录不可变的来源路径与 SHA-256。
- publish freshness 应读取锁内来源清单并核对哈希；发现共享文件已被后续时段覆盖时，读取 slot 快照，不得借新文件 mtime 放行。
- 默认发布始终保留 240 分钟实时可执行源硬门。若用户明确要求继续交付已锁定时点报告，只能通过 `publish_report.py --allow-locked-timepoint-publish --locked-timepoint-reason <reason>` 执行；该通道必须机械验证 analysis lock、报告 hash、capture manifest hash 与 immutable snapshot，并在 publish manifest 保留原 freshness 失败和用户授权原因。
- 跨时段只允许在各自分析锁完成后做“事后漂移对照”，不得回写前序样本。
